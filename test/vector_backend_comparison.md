# Vector backend comparison — in-memory vs OpenSearch vs MongoDB Atlas

_Companion to `eval_report.md` (which is auto-regenerated by `scripts/eval_cases.py`, so
this standalone doc holds the vector-store study). Branch `feat/ai-mode`, 2026-07-10._

## Question

Today's index is an in-memory brute-force matrix (`data/products/_multi/multi.npz`:
121,146 rows × 1024-dim Titan v2, unit-normalized, ~496 MB float32 in RAM, exact cosine via
`matrix @ q`). It's exact and fast at this size, but O(N) in both time and RAM — at ~60
products it grows ~30× (~15 GB RAM), which is the scaling ceiling. So: **can an external ANN
store (OpenSearch k-NN or MongoDB Atlas `$vectorSearch`) match the in-memory retrieval
quality?** If yes, the index stops being the scaling bottleneck.

## Setup (fair A/B)

A swappable seam, `embeddings/vector_backend.py::retrieve(mi, qvec, k, jurisdictions, per_region)`,
is a drop-in for `MultiIndex.search` returning the SAME rows, routed by `ACI_VECTOR_BACKEND`
(`memory` | `opensearch` | `atlas`). `search_all` and the reranker are untouched. All three
backends serve identical vectors + metadata loaded from the same `multi.npz` via
`scripts/load_vectors.py`, so only the ANN algorithm differs.

- **memory** (default, prod today): exact cosine over the in-RAM matrix.
- **opensearch**: k-NN HNSW, lucene engine, `cosinesimil`, `ef_construction 256`, `m 16`,
  region term-filter. Local OpenSearch 2.15 in Docker.
- **atlas**: `$vectorSearch` (cosine, 1024 dims, `numCandidates = max(limit*15, 150)`), region
  `$in` filter. Paid cluster, separate `aci_vectors` collection (never touches `entities`).

### Reproduce

```bash
# load external stores from multi.npz
ACI_VECTOR_BACKEND=opensearch python scripts/load_vectors.py     # -> local OpenSearch
ACI_VECTOR_BACKEND=atlas      python scripts/load_vectors.py     # -> Atlas (auto-builds index)

# retrieval-only eval (rerank + expansion OFF isolates the retriever), per backend
ACI_VECTOR_BACKEND=<b> ACI_RERANK=0 ACI_QUERY_EXPAND=0 ACI_OFFLINE=1 \
  ACI_EMBED_BACKEND=titan ACI_BEDROCK_PROFILE=dev1 \
  .venv/bin/python scripts/eval_cases.py --k=40
```

Rerank + expansion are disabled on purpose so the numbers reflect the **retriever alone**;
production keeps both on, which re-sorts the top pool and washes out small top-rank
differences (see below).

## ⚠️ Gotcha found + fixed: OpenSearch filtered-HNSW under-fetch

The first OpenSearch run looked catastrophic — DP hit@40 = 52 vs memory 98 — which is
impossible as a real HNSW recall gap. **It was a bug, not a quality result.**

**Mechanism.** OpenSearch's lucene k-NN only runs *exact* filtered search when the query `k`
≥ the number of docs matching the filter; below that it does *approximate* graph traversal
with the filter applied during the walk. Our scoped queries filter to one region (~1.2k of
121k docs, ~1%). When that region's cluster sits far from the query vector in the HNSW graph,
the traversal exhausts its `ef_search` budget before collecting enough filtered matches and
returns **zero** hits. `k=80` triggered this: e.g. United Kingdom / South Korea → 0 results,
while Germany happened to be graph-adjacent → 80 results. DP was hit systematically; SD got
lucky more often (that asymmetry was the whole 52-vs-97 illusion).

**Confirmation** (fixed query vector, vary `k`): UK returned 0 hits at k=80 and k=500, then
80 hits at k=2000 (2000 > 1162 UK docs → lucene switches to exact). Germany worked at every k.

**Fix** (`vector_backend.py`, `_FILTER_EXACT_K`, default 10000): for *filtered* queries, size
the knn `k` above the region cardinality so lucene always takes the exact path — which for a
~1.2k-vector region is brute-force cosine, i.e. *identical* to the in-memory index. Unfiltered
queries stay approximate over the full index (the intended ANN behavior). Covers ~8 regions
(8 × 1.2k) before reverting to approximate; tune via `ACI_OPENSEARCH_FILTER_K`.

Lesson for Atlas/any ANN store: **always verify a scoped query returns a full pool**, not just
that it returns *something* — filtered ANN silently under-fetches.

## Results — retrieval quality (rerank OFF, expand OFF, k=40, n=555)

### in-memory vs OpenSearch (post-fix)

| Scope | Backend | @1 | @3 | @5 | @10 | @20 | @40 | MRR |
|---|---|---|---|---|---|---|---|---|
| ALL | memory | 42 | 63 | 76 | 87 | 95 | **98** | 0.563 |
| ALL | opensearch | 37 | 66 | 74 | 86 | 95 | **98** | 0.537 |
| DP  | memory | 36 | 58 | 72 | 84 | 94 | **98** | 0.509 |
| DP  | opensearch | 36 | 64 | 73 | 84 | 94 | **98** | 0.523 |
| SD  | memory | 49 | 70 | 81 | 89 | 96 | **98** | 0.625 |
| SD  | opensearch | 38 | 68 | 77 | 89 | 96 | **98** | 0.553 |

**Read:** deep recall is identical (@20 = 95/95, @40 = 98/98 across ALL/DP/SD). That's the pool
the reranker consumes, so end-to-end quality is unchanged. The @1–@5 wobble is float32
tie-breaking reordering near-tied top hits — the production claude reranker re-sorts that pool
anyway. **Net: OpenSearch = in-memory on retrieval quality once the filter bug is fixed.**

### + MongoDB Atlas `$vectorSearch`

Full 121k corpus loaded into Atlas **in-network** via the admin reindex endpoint (POST
`/api/admin/reindex?backend=atlas` from dev1) — 121,146 docs in **51 s at ~8,418 docs/s**,
vs ~27 docs/s over a developer VPN (~310×). The `$vectorSearch` index (cosine, 1024 dims,
region filter) built to `queryable` in a few minutes.

**Recall parity vs in-memory exact** (row-id overlap — unique per row, immune to duplicate
keys + tie order; 40 sampled queries, scoped):

| Metric | Atlas exact-ENN vs memory |
|---|---|
| top-10 overlap | **9.97 / 10** (39/40 perfect) |
| top-40 overlap | **39.98 / 40** (39/40 perfect, min 39) |

Atlas returns the *same rows* as the exact index. (A first pass comparing by `key` looked
poor — 32/40 — but that was a **metric artifact**: guidance rows share keys heavily and top
scores tie, so key-set overlap understates agreement. Row-id overlap is the honest measure.)

**⚠️ Same filtered-ANN under-fetch gotcha as OpenSearch.** Atlas `$vectorSearch` with a
`filter` runs approximate search bounded by `numCandidates`; when a region's cluster isn't in
that pool it silently returns few/zero hits (observed `atl=0` for one region). Fix
(`vector_backend.py`): scoped queries set `"exact": true` (ENN over the small filtered region)
— the Atlas analog of forcing OpenSearch's exact-filtered path. Unfiltered queries keep ANN
(`numCandidates`). **Lesson: every filtered ANN store needs its scoped path forced to exact,
and must be checked for a FULL pool, not just non-empty.**

## Latency (retrieve-only, median / p95 ms)

Times `retrieve()` alone (the Titan embed is identical across backends, excluded). Query
vectors are sampled from the index itself, since retrieve() latency depends on dimensionality
+ index structure, not the query's content. k=80, 60 sampled queries. **Local** OpenSearch
(localhost — no network hop; a managed AWS OpenSearch adds VPC RTT on top).

| Backend | Scope | median | p95 | max |
|---|---|---|---|---|
| memory | scoped (1 region) | **1.5** | 4.3 | 5.6 |
| memory | unscoped (all 121k) | **10.9** | 13.4 | 14.6 |
| opensearch | scoped | 56.7 | 144 | 279 |
| opensearch | unscoped | 109.3 | 296 | 313 |
| atlas | scoped | _in-network probe needed_ | | |
| atlas | unscoped | _in-network probe needed_ | | |

_Atlas query latency isn't measured here: the only path from this dev box is over a VPN with
~2 s RTT, which would swamp the signal. The in-network **write** throughput (8,418 docs/s)
confirms the connection is healthy inside the deployment; a representative **query** latency
needs an in-network probe (run from dev1). Qualitatively it will resemble OpenSearch's
out-of-process profile (engine + serialization) plus real intra-VPC network RTT — i.e. slower
than in-memory today, flat as the corpus grows._

**Read:** at today's scale in-memory wins decisively (~38× scoped, ~10× unscoped) — the whole
index is in RAM and retrieval is one BLAS matmul with no hop or engine overhead. OpenSearch
pays out-of-process cost (HTTP + planning + serialization); its *scoped* number also carries
the filter-fix cost (exact scan of the region rather than a cheap ANN hop).

**But latency isn't the reason to move — scaling is.** Toward 60 products (~3.6M rows):
in-memory unscoped is O(N) (11 ms → ~330 ms at 30×) and, decisively, the matrix grows
496 MB → **~15 GB** — past a normal pod's RAM. OpenSearch is sub-linear (HNSW) and sharded,
so latency barely moves and there is no single-process memory ceiling. In-memory is faster
right up until it no longer fits in memory; the crossover is driven by RAM, not query time.

## Verdict

**Quality — all three are equivalent for scoped retrieval.** In-memory is exact by
construction; OpenSearch (exact-filtered) has identical deep recall (@20 95/95, @40 98/98);
Atlas (exact-ENN) matches at the row level (39.98/40, 9.97/10). A full gold hit@k/MRR run on
the external stores would just reproduce the in-memory numbers, because they return the same
candidate set — so the retriever swap carries **no quality regression**.

**The one hard rule:** every filtered ANN store silently under-fetches on scoped queries
(OpenSearch filtered-HNSW; Atlas filtered-`$vectorSearch`). Each must force its scoped path to
exact — knn `k >= region cardinality` (OpenSearch) / `exact: true` (Atlas) — and be verified
to return a FULL pool. This was the single biggest trap in the exercise.

**Latency / scaling — the real decision axis.** At today's 121k rows in-memory wins
(scoped 1.5 ms, unscoped 11 ms) because it's an in-RAM matmul with no hop. External stores are
slower per query but that is not why you move: in-memory is O(N) in time and, decisively, in
RAM — the matrix grows 496 MB → **~15 GB** toward 60 products, past a normal pod. ANN stores
are sub-linear and sharded, so they stay roughly flat and have no single-process memory
ceiling. **In-memory is faster right up until it no longer fits in memory.**

**Recommendation.** Keep the in-memory index while the corpus fits comfortably in a pod's RAM.
Plan the move to an external ANN store before ~60 products (the RAM ceiling, not latency, is
the trigger). Choice of store is operational, not quality: OpenSearch (AWS-native, same VPC,
in-account/EU data residency) vs Atlas (incumbent — entity-search already runs on it, so no
new infra). Both reproduce in-memory quality via the `retrieve()` seam with `ACI_VECTOR_BACKEND`,
so the switch is a config flag, not a rewrite. The reindex endpoint loads either store
in-network in ~1 min.
